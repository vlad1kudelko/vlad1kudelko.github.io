# HTTP 200 при сорванном входе: где измерять доступность

API принял запрос на двухфакторную аутентификацию, поставил сообщение в очередь и вернул 200 OK. Push задержался по пути к смартфону, сессия истекла. На дашборде веб-сервера всё зелёное, пользователь остался перед закрытым VPN. Для асинхронного сервиса такой разрыв между метриками и результатом заложен в самой цепочке доставки.

У 2FA эта цепочка проходит через API, очередь отправки, Apple APNs, Google FCM или Huawei, магистральные сети, мобильного оператора и приложение. Подтверждение на телефоне завершает сценарий. Успешный ответ первого звена ничего не говорит о времени прохождения остальных.

## Что защищает Active-Active

Две активные площадки позволяют пережить отказ дата-центра. Входящий трафик можно распределять через CDN с непрерывными healthcheck и переключать при росте задержки или проблемах сетевого канала. Третий изолированный ЦОД подходит для резервных копий и асинхронной репликации MongoDB. Приложения при этом должны корректно переживать перевыборы Primary.

Межплощадочный транспорт тоже требует проверки на реальных задержках. В инфраструктуре 2FA при попытке распределить RabbitMQ через Federation/Shovel возникали split-brain, блокировки очередей и проблемы с кворумом. Переход на NATS Core упростил эксплуатацию и веерную доставку между площадками. Этот опыт относится к конкретной конфигурации; переносить выбор брокера на другую систему без проверки её требований рискованно.

Даже исправные площадки и брокер оставляют внешнюю push-доставку за границей контроля команды. Для неё нужен отдельный сигнал о прохождении пользовательского сценария.

## Как задержка доставки превращается в шторм

Во время утреннего пика авторизаций замедление маршрутов до push-шлюзов вызывает рост буферов отправки. Пользователь ждёт две-три секунды и повторяет вход. Повторные попытки увеличивают очередь, подтверждение приходит ещё позже, число новых попыток растёт.

Внутренние серверы в такой ситуации могут работать штатно. Диагностические признаки находятся в других местах: растёт насыщение очередей, падает доля завершённых авторизаций, увеличивается время полного входа.

Практический способ увидеть проблему — синтетическая петля из-за пределов инфраструктуры:

1. Раз в 30 секунд агент запускает настоящую авторизацию тестовой учётной записи.
2. Ожидает push на виртуальном устройстве.
3. Программно подтверждает вход.
4. Измеряет длительность всего сценария.

Две последовательные ошибки или превышения порога по времени открывают инцидент для дежурной смены. Такая проверка проходит участок, который обычный HTTP healthcheck пропускает.

## Конверсия и её слепые зоны

Базовый показатель для работающего потока запросов — доля успешных подтверждений:

```text
conversion = успешные события 2FA (granted) / все запросы на 2FA
```

Его нужно смотреть вместе с объёмом трафика. Если сетевой сбой отрезал пользователей от API, запросы перестанут поступать. При нуле запросов и нуле подтверждений отношение вообще не определено. Чистый график HTTP-ошибок тоже ничего не доказывает: до сервера мог никто не добраться.

Для такого случая полезен алерт по отклонению числа событий от сезонного baseline. В нём учитываются суточные паттерны нагрузки: утренний поток входов и ночное затишье имеют разные ожидаемые значения. Резкое исчезновение привычного трафика становится отдельным сигналом.

Внешние проверки закрывают ещё одну часть картины. Они показывают доступность API из разных сетей и регионов. В ответе полезно проверять JSON-поля или ожидаемое содержимое: заглушка и пустой ответ бэкенда тоже могут прийти с кодом 200. Подтверждение сбоя несколькими локациями помогает отсеивать локальные сетевые флапы. MTR и DNS-трассировка, снятые во время инцидента, сохраняют данные для разбора маршрута.

## Как учитывать частичную деградацию

Конверсия зависит от обычного поведения пользователей, поэтому для неё строят сезонную медиану и допустимый коридор колебаний. Падение ниже нижней границы служит условием фиксации деградации. Выбор коридора определяет, какие отклонения команда будет считать расходом бюджета ошибок.

Частичный сбой можно выразить через эквивалентное время простоя. Например, если конверсия в течение 20 минут была на 20% ниже допустимой нижней границы:

```text
EquivalentDT = 20 минут × 0,2 = 4 минуты
```

Здесь 20% — относительная глубина провала относительно выбранной границы. Двадцать минут деградации сохраняются в хронологии инцидента, а четыре минуты используются в расчёте эквивалентного простоя. Метод расчёта и границы нужно согласовать заранее, иначе одинаковые события будут получать разные оценки.

## Что оставить пользователю при отказе push

Direct Polling позволяет открытому мобильному приложению напрямую опросить API ядра и получить ожидающий запрос, обходя внешний push-транспорт. Дополнительные варианты подтверждения — локальный код TOTP и аппаратный токен FIDO2/WebAuthn. Доступность этих сценариев зависит от заранее настроенных факторов и поддержки со стороны системы входа.

Во время инцидента статус-страница должна сообщать, какой канал деградировал и какой из предусмотренных способов входа доступен. Это даёт пользователю действие вместо повторного нажатия на тот же сломанный сценарий и уменьшает поток обращений в поддержку.

Для рабочего дашборда достаточно начать с четырёх связанных сигналов: доли успешных входов, длительности синтетической петли, отклонения объёма запросов от baseline и результатов внешних проверок. Метрики очередей, репликации и подов помогают локализовать причину. Сквозной результат показывает, смог ли пользователь войти.
