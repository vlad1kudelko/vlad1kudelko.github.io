# Подготовленные выражения меняют стоимость работы API

Rust может тратить на обработку HTTP-запроса меньше CPU, чем Go, и при этом требовать больше процессорного времени вместе с PostgreSQL. В замере небольшого JSON API получилось именно так: 0,27 мс у Rust против 0,40 мс у Go на стороне приложения, но 1,71 мс против 0,92 мс в сумме с базой. Разницу создало поведение драйверов при подготовке SQL.

Это полезный повод проверить конфигурацию доступа к данным перед переносом сервиса на другой язык. На повторяющихся коротких запросах расходы PostgreSQL на разбор SQL могут превышать весь расход CPU веб-приложения.

## Что измеряли

Одинаковый API реализовали в 12 вариантах на восьми языках. В набор вошли четыре модели запуска PHP, два варианта Node.js, Go, Rust, Java, .NET, Python и Ruby. API проверял токен в базе и отдавал посты с авторами, тегами и числом комментариев. Для страницы списка требовалось четыре SQL-запроса. Данные Symfony Demo увеличили в 100 раз, ответы реализаций канонизировали и сверяли по хешу.

Нагрузку держали на уровне 2000 HTTP-запросов в секунду через wrk2. Процессорное время контейнеров приложения и базы считали отдельно и делили на количество обслуженных запросов. Поэтому миллисекунды в таблице обозначают **затраты CPU на запрос**. По этим числам нельзя узнать время ожидания ответа клиентом.

Стенд работал на Ryzen 9 5950X. Приложению выделили четыре ядра с восемью логическими потоками, PostgreSQL и генератор нагрузки разместили на других ядрах той же машины. Использовали PostgreSQL 17.11; результаты — медианы минимум трёх проходов. Медианный разброс CPU приложения между проходами составлял 1,2%, поэтому различия соседних строк на пару процентов мало что доказывают.

## Где образовался разрыв

Часть результатов для PostgreSQL, в миллисекундах CPU на HTTP-запрос:

| Стек | Приложение | PostgreSQL | Сумма |
| --- | ---: | ---: | ---: |
| Java Jetty, виртуальные потоки | 0,30 | 0,52 | 0,82 |
| Go net/http | 0,40 | 0,52 | 0,92 |
| Python uvicorn | 0,40 | 0,58 | 0,98 |
| Node node:http | 0,37 | 1,26 | 1,64 |
| Rust hyper | 0,27 | 1,44 | 1,71 |
| PHP FPM + nginx | 0,51 | 1,50 | 2,01 |

Для Go, Java и Python база тратила около половины миллисекунды. У остальных вариантов расход PostgreSQL составлял примерно 1,2–1,5 мс. Собственная экономия Rust на обработке HTTP в такой конфигурации терялась на стороне SQL.

Три стека с меньшим расходом базы использовали pgx, PgJDBC и asyncpg. Эти драйверы по умолчанию сохраняли подготовленные выражения на соединении и использовали их повторно. PostgreSQL мог пропустить повторный разбор SQL, а при выборе generic plan — ещё и построение плана.

У другой группы поведение отличалось. node-postgres, Ruby pg и Npgsql отправляли безымянные подготовленные выражения. tokio-postgres и pdo_pgsql при обычном вызове подготавливали, выполняли и закрывали выражение для каждого SQL-запроса. В результате одинаковый SQL снова проходил подготовку.

## Две настройки, которые проверили отдельно

В дополнительной серии меняли по одной опции подключения. Это позволило проверить влияние настройки внутри одного стека:

- **pgx без кеша выражений:** расход CPU базы вырос с 0,53 до 1,21 мс на HTTP-запрос. Собственный расход Go практически сохранился.
- **Npgsql с `Max Auto Prepare=20`:** расход PostgreSQL снизился с 1,29 до 0,59 мс. CPU приложения уменьшился примерно на 7%.

Обе проверки сдвинули расход базы примерно вдвое. Для API с повторяющимися SQL-запросами настройка повторного использования выражений заслуживает отдельного замера.

Сохранённое выражение при этом не гарантирует один план навсегда. PostgreSQL может строить custom plan для очередного выполнения с конкретными параметрами. Переиспользование разбора SQL и переиспользование плана — разные механизмы, и при диагностике их нужно разделять.

## Что проверить в работающем сервисе

Начать можно с `pg_stat_statements`: включить учёт планирования через `pg_stat_statements.track_planning` и сравнить прирост `plans` и `calls` за один интервал. Если планы строятся почти при каждом выполнении, следующий шаг — проверить режим работы драйвера и жизнь подготовленных выражений на соединении.

Само соотношение счётчиков причину не устанавливает: частое планирование возможно и при сохранённых выражениях из-за custom plans. Кроме того, `track_planning` способен заметно нагружать CPU при большом числе соединений с одинаковыми запросами. Эту цену нужно учитывать во время измерения.

Дальнейшая проверка зависит от клиента:

- Для **Npgsql** — замерить автоматическую подготовку с `Max Auto Prepare`.
- Для **deadpool-postgres** — проверить применение `prepare_cached`.
- Для **PDO с PostgreSQL** — проверить PgBouncer с `max_prepared_statements` или отдельно оценить эмуляцию подготовки через `PDO::ATTR_EMULATE_PREPARES`.

Последние два подхода меняют работу с запросами разными способами. PgBouncer помогает переиспользовать подготовленные выражения, эмуляция в PDO сокращает число обменов с базой. В отдельном замере при полной загрузке PostgreSQL эмуляция снизила суммарный CPU FPM и базы на 18%, PgBouncer — на 27%. Эти проценты относятся к конкретному API и режиму нагрузки.

## Медленный внешний API меняет расход памяти

Для CPU и памяти в эксперименте использовали разные сценарии. Во второй серии каждый HTTP-запрос ждал внешний сервис одну секунду. Число клиентов повышали со 100 до 1000, затем разницу памяти пересчитывали на дополнительную тысячу ожидающих запросов.

У FPM прирост составил 1,13 GiB, у FrankenPHP — 0,96 GiB, у Swoole — 0,11 GiB, у Rust — 0,08 GiB, у Python uvicorn — 0,02 GiB. Это прирост относительно первой точки нагрузки: всего при 1000 клиентах Python занимал 301 MiB, Rust — 90 MiB.

Для блокирующих моделей стенд выделял воркер на ожидающий запрос. Такая схема показывает цену наращивания параллелизма; фиксированный пул в продакшене при исчерпании воркеров начнёт накапливать очередь. Особенно дорого получилось у RoadRunner: на 500 клиентах он занимал 5,8 GiB и упирался в ограничение 500 воркеров.

Поэтому снижение CPU базы и выбор модели обработки ожидающих запросов требуют отдельных проверок. Результаты короткого SQL API ничего не говорят о памяти сервиса, который держит сотни запросов к медленному upstream.

## Границы этих чисел

Все реализации были минимальными, без ORM, кешей, логирования и полноценных прикладных фреймворков. Код создавали с LLM, ответы сверяли, но сообщества языков реализации ещё не проверяли. Приложение, база и нагрузчик общались через loopback одной настольной машины с включённым Precision Boost. В облаке к расходам добавятся сетевые прерывания и другие условия исполнения.

Для собственного API пригодится тот же порядок проверки: раздельно измерить CPU приложения и PostgreSQL, выяснить поведение драйвера, изменить одну настройку и повторить нагрузку. Если основная доля времени уходит на повторную подготовку SQL, начинать оптимизацию можно с подключения к базе, сохранив текущий язык и HTTP-сервер.
