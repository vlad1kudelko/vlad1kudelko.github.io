# Как читать графики сервиса после переезда контейнера

Docker Swarm перезапускает задачу, меняет её идентификатор и может перенести контейнер на другую ноду. Если история мониторинга привязана к `task.id`, очередной запуск разрывает ряд метрик. Найти медленную утечку памяти становится трудно: вместо месяца жизни сервиса видны отдельные отрезки между перезапусками.

Для связки Zabbix и Grafana нужны две вещи: стабильная идентичность метрики внутри Zabbix и понятные теги для выбора данных снаружи. Поверх графиков полезно наложить события оркестратора — смену задачи и миграцию. Тогда скачок памяти можно сопоставить с релизом, а падение — с переездом на другую ноду.

## Разделить идентичность и подписи

У метрик контейнера и данных оркестрации разные источники. Канал метрик получает готовое имя контейнера от Docker-плагина. Канал оркестрации собирает его из полей ответа Portainer API. На выходе оба канала должны давать согласованный набор признаков:

| LLD-макрос | Смысл | Пример |
| --- | --- | --- |
| `{#STACK.NAME}` | Имя стека | `cd-my-web` |
| `{#SERVICE.NAME}` | Полное имя сервиса | `cd-my-web_backend` |
| `{#SERVICE.SHORT}` | Короткое имя сервиса | `backend` |
| `{#NODE.SHORT}` | Короткое имя ноды | `node4` |
| `{#SLOT}` | Слот реплики или признак global | `1` либо `global` |

Стабильные ключи каналов метрик и оркестрации остаются внутренним механизмом Zabbix. Для фильтрации и подписей в Grafana используются отдельные теги. Склейка стека, сервиса и ноды в одну строку с разделителями усложняет панели: каждую приходится дополнять преобразованиями и правилами `setAlias`.

Раздельные поля позволяют одинаково описать сервис с одной репликой, несколько реплик, многосервисный стек и глобальный сервис. У последнего на каждой ноде работает собственная задача, поэтому на графике нужны отдельные линии по нодам.

## Передать стек в Grafana через теги

Виртуальные узлы-стеки можно создавать через обнаружение Zabbix. Узел оркестратора получает шаблон `LLD_HOST`, а обнаруженные узлы попадают в группу `Docker Swarm Stacks`.

Из `{#STACK.NAME}` формируются два значения с разными областями применения:

- макрос уровня узла `{$STACK_NAME}`, например `cd-my-web`, для внутренней фильтрации Zabbix;
- тег элемента данных `stack=cd-my-web`, доступный для фильтрации в Grafana.

Теги задаются в прототипах элементов данных внутри `LLD_STACK`. Дополнительная метка вроде `metric_group=memory` помогает выбирать группу показателей. В Grafana переменная типа Query с именем `$stack` становится фильтром всего дашборда: выбор стека переключает связанные панели без ручного редактирования регулярных выражений в каждой из них.

Для подписей миграций пригодится отдельный элемент `Orch: Node location (Pretty)`. Он помогает показать, какой сервис сменил ноду. У глобального сервиса такую панель можно отключить через Override: распределение по нодам уже является частью его обычной структуры.

## Собрать ресурсы, размещение и завершения на одном экране

Дашборд для расследования перезапусков должен одновременно показывать историю и последнее состояние. Удобный набор панелей:

- **Memory и CPU** — потребление ресурсов до события и после него;
- **Node location** — последовательность нод, на которых работал сервис;
- **Network Tx/Rx** — всплески трафика и периоды простоя;
- **PIDs current** — изменение количества процессов;
- **OOM Killed и Exit Code** — признаки последнего завершения.

Аннотации Zabbix накладываются поверх временных рядов. События `Task ID changed` и `Migrated to another node` дают временные отметки для сравнения. Если линия памяти проходит через отметку перезапуска, история сохранилась. Если каждый такой пунктир начинает отдельную серию, стабильность идентификации стоит проверить до дальнейшей настройки визуализации.

Код завершения следует читать вместе с остальными сигналами. Значение `137` совместимо с принудительным завершением процесса; для вывода об OOM нужен соответствующий признак. Код `71` в конкретном приложении может сопровождать ошибку доступа к БД, но сам по себе не объясняет её причину. За деталями придётся обратиться к журналам приложения.

## Увеличить окно до месяца

Недельный график может скрыть плавный рост памяти. На месячном окне удобнее сравнивать наклоны линий отдельных сервисов и искать устойчивый тренд. Сохранённая история позволяет проверить несколько практических гипотез.

**Ресурсы выделены с большим запасом.** Если потребление долго держится около 10–15% лимита, появляется основание пересмотреть выделение памяти. Для решения пригодятся и пики нагрузки: среднее потребление само по себе их не описывает.

**Процессор ограничен квотой.** Историю `container.cpu.throttled_time` можно сопоставить с нагрузкой и лимитами CPU. Длинный интервал помогает увидеть повторяющиеся периоды троттлинга.

**Релиз изменил потребление.** Аннотация смены задачи задаёт точку сравнения. Рост памяти на 20% после обновления заметен ещё до первого OOM, если ряд продолжился через перезапуск.

**Растёт количество процессов.** Динамика `PIDs current` показывает, когда началось увеличение. Этот график даёт направление для проверки поведения приложения.

**Изменился сетевой профиль.** Повторяющийся ночной пик можно сопоставить с резервным копированием или заданием cron. Десятикратный рост трафика без понятного события требует отдельного расследования.

## Разобрать цикл падений через временную шкалу

Предположим, после обновления CPU начинает колебаться, память скачком вырастает на 1 ГБ, а контейнер завершается с кодом `71`. На полосе размещения видны повторные смены нод. Эти события описывают последовательность сбоя; установить причину по одним графикам ресурсов нельзя.

Если в логах одновременно появляется `ORA-12526` — отказ подключения Oracle из-за restricted mode, — проверка смещается к обработке недоступности БД. Для такого сценария нужны ограниченные попытки подключения, тайм-ауты, задержка между повторами и предусмотренное поведение при старте. Требования к `restart_policy` должны быть согласованы с этой логикой.

Метрики пула соединений сокращают путь от симптома к причине. Рядом с ресурсами полезно иметь `hikaricp_connections_pending`, `hikaricp_connections_timeout_total` и счётчик ошибок соединения вроде `db.connection.failures`, если приложение их экспортирует. Тогда рост CPU можно сопоставить с очередью подключений и ошибками БД в том же временном окне.

Проверять готовность такого мониторинга удобно на контролируемом перезапуске и миграции сервиса. Ряд ресурсов должен продолжиться, размещение — обновиться, а аннотация — попасть на нужную временную отметку. После этого месячный график уже пригоден для сравнения релизов и поиска медленных изменений потребления.
