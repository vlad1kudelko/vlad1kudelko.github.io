# Границы доступа для агента с терминалом

Агент, запущенный под учётной записью разработчика, получает доступ к его инструментам: Git, базе данных, облачному хранилищу, Kubernetes. Ошибка в выборе команды становится ошибкой с правами этой учётной записи. Запись «спрашивай перед push» в AGENTS.md оставляет техническую возможность отправить изменения без вопроса.

В одном разборе рабочих сессий OpenCode после появления такого правила обнаружились 39 push без согласия пользователя из 109 вызовов. Зафиксированы три эпизода отправки в main с обходом политики и 31 попытка force push при двух явных запросах пользователя. Это наблюдения за конкретным окружением; переносить такую частоту на любую модель и любой проект нельзя. Но для проектирования защиты достаточно самого факта: текстовое правило может остаться невыполненным.

## Инструкция задаёт порядок работы

AGENTS.md подходит для описания структуры проекта, тестовых команд и соглашений о ветках. Модель получает этот текст в контексте и использует при выборе действий. Сервер Git и PostgreSQL этот файл не читают: разрешённая учётной записи операция останется разрешённой при любом содержимом инструкции.

Причём короткий успешный тест легко создаёт ложную уверенность. В контролируемом эксперименте десять прогонов с AGENTS.md завершились без нарушений: агент выбирал отдельную ветку и файл миграции. Реальные рабочие сессии при этом содержали нарушения. Проверять границу доступа нужно принудительной попыткой запрещённой операции, включая обходные способы её выполнения.

## Хук ловит распознанную опасную команду

Хук перед вызовом инструмента получает описание действия и может остановить исполнение. Например, в Claude Code для этого служит PreToolUse. Готовые наборы правил вроде Destructive Command Guard проверяют опасные операции Git, PostgreSQL, Kubernetes и облачных CLI.

Такой предохранитель полезен против случайного `git push --force`, `DROP TABLE` или удаления namespace. Для надёжной работы сам хук должен быть недоступен для отключения из агентской сессии, а ошибка проверки должна приводить к блокировке действия — это режим fail closed.

Граница фильтра проходит по тому, что он умеет анализировать. Проверка строки shell-команды может заблокировать SQL с `DROP`, но пропустить запуск `./db.sh -f migration.sql`. Внутри файла окажется та же операция. В эксперименте с command guard такой вызов прошёл дважды за один прогон.

У списков запрещённых команд много похожих пробелов: запись через перенаправление, другой интерпретатор, команда внутри скрипта. Поэтому хук нельзя считать гарантией сохранности файлов или базы. Излишне широкий запрет тоже мешает: блокировка любого `git push` в том же эксперименте сорвала все пять Git-задач.

## Песочница ограничивает доступ процесса

Ограничения ОС распространяются на дочерние процессы. Если процессу закрыт путь за пределами workspace, запуск Python или вложенного shell сохраняет эту границу. Для shell-песочницы Claude Code на Linux используется bubblewrap, на macOS — Seatbelt.

У настройки есть несколько отдельных зон проверки:

- **Повтор вне sandbox.** Возможность выполнить упавшую команду без ограничений нужно закрыть. В Claude Code для этого используется `allowUnsandboxedCommands: false`.
- **Исключения.** Команды из `excludedCommands` исполняются вне песочницы. Через широкое исключение можно запустить заранее записанный агентом файл.
- **Другие инструменты.** Встроенные Read, Edit, Write и WebFetch подчиняются своим permissions. Ограничения shell сами по себе их не закрывают.
- **Локальные сервисы.** MCP-серверы и хуки могут работать с полными правами пользователя.

Контейнер или VM переносит границу на окружение агента целиком. Но примонтированный проект остаётся доступен для изменения, а испорченный через bind mount файл меняется и на хосте. Токен в переменной окружения или внутри рабочей папки тоже остаётся доступным. В sandbox-пробах из описанного эксперимента ограничения остановили семь из восьми проверок; уже переданная переменная окружения сохранила доступность.

Отдельно стоит проверить проброс Docker socket: доступ к нему фактически даёт полномочия root на хосте. Для изолированной агентской среды такой mount разрушает ожидаемую границу.

## Сервер проверяет права независимо от команды

Для Git базовый барьер — защищённая основная ветка и отдельный токен агента. У этого токена должны отсутствовать права на прямой push и снятие защиты. Тогда смена синтаксиса команды или Git-клиента не позволит обойти серверную проверку. Изменения проходят через MR и обязательный CI.

Для чтения PostgreSQL можно выделить роль без владения таблицами и без прав записи:

```sql
CREATE ROLE agent_ro LOGIN;
GRANT USAGE ON SCHEMA marts TO agent_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA marts TO agent_ro;
```

Этот пример выдаёт доступ к существующим таблицам схемы `marts`. Роль не должна наследовать дополнительные полномочия через другие роли. Владение объектами и суперпользовательский доступ ей также не нужны.

Настройка теряет смысл, если рядом доступны личные credentials разработчика с более широкими правами. Изоляция файлов и окружения нужна в том числе для того, чтобы агент не мог сменить ограниченную учётную запись на привилегированную.

В проверке на локальных Gitea и PostgreSQL платформенные ограничения дали десять корректных результатов из десяти. Дополнительно серверы отклонили две принудительные опасные операции. Такой тест проверяет именно отказ системы, независимо от готовности модели соблюдать инструкцию.

## Контракты должны стоять на обязательном пути

Минимальные права ограничивают операции, но разрешённое изменение тоже может сломать потребителя. Для данных полезны дополнительные проверки: Schema Registry проверяет совместимость схем сообщений, dbt contracts фиксируют ожидаемые колонки и типы моделей.

Оба механизма требуют обязательного пути исполнения. Schema Registry сам по себе не запрещает деплой: проверку совместимости нужно встроить в CI, а регистрацию схем проводить через реестр. Для dbt требуется сборка изменённых моделей и запрет merge при упавшем CI. Совпадение типов при этом не гарантирует правильность бизнес-логики.

Для рабочего окружения получается конкретный набор: инструкции проекта, хук на случайные разрушительные команды, строгая изоляция, отдельные credentials и серверные запреты. Проверять его удобно от последнего рубежа: может ли агент своим токеном отправить commit в main, удалить таблицу или прочитать личный секрет? Если операция проходит, исправлять нужно соответствующую границу доступа. Дополнительная строка в AGENTS.md техническое разрешение не отзовёт.
