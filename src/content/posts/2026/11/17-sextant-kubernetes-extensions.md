# Что меняется в клиенте Kubernetes после разделения ядра и интеграций

У клиента Kubernetes быстро накапливаются специальные экраны: состояние Flux, сертификаты cert-manager, резервные копии PostgreSQL, очереди задач. Каждый установленный оператор приносит собственные ресурсы и правила диагностики. Когда вся эта поддержка встроена в приложение, исправление одной интеграции привязано к выпуску клиента целиком.

В Sextant 0.30 из ядра вынесли 31 интеграцию. Объём TypeScript-кода окна сократился с 209 до 170 тысяч строк. Вместе с Rook Ceph, который изначально разрабатывался отдельно, каталог команды содержит 32 расширения. У каждого собственная версия и цикл выпуска: обновление поддержки Knative можно доставить отдельно от самого клиента.

Sextant — бесплатное десктопное приложение для Kubernetes на Rust и Tauri 2 со встроенным MCP-сервером. Перестройка затрагивает и повседневную работу с кластером, и устройство SDK для разработчиков интеграций.

## Что остаётся в основном приложении

В ядре сохранены таблицы ресурсов, просмотр деталей, редактор, логи, терминалы, Helm, метрики, диагностика проблем, RBAC, сетевые политики и Gateway API. Там же работают MCP-сервер и платформа расширений.

Отдельными пакетами стали GitOps-инструменты Flux и Argo CD, сервисные сети Istio и Linkerd, cert-manager, External Secrets, CloudNativePG, Strimzi, Velero, KEDA, Karpenter, Crossplane и другие интеграции. Это позволяет выбирать поддержку под состав конкретного кластера.

После обновления боковое меню предлагает установить расширение для обнаруженного инструмента. Его разделы занимают прежние места. Настройки уведомлений и доступа агентов к проблемам однократно переносятся на новые категории. Для администратора здесь существенны две вещи: сохранение привычной навигации и отдельное управление версиями интеграций.

## Три слоя с разной ценой выполнения

Архитектура расширения начинается с манифеста. В нём описываются виды ресурсов, вычисляемые колонки, правила диагностики, счётчики в меню, фиксированные патчи, запросы метрик и команды в подах. Эти данные обрабатывает сам Sextant; исполняемый код расширения для такой работы запускать не требуется.

В 32 расширениях таким способом заданы 196 видов ресурсов, 736 колонок и 354 правила. На таблице из 20 тысяч объектов вычисление колонок внутри хоста избавляет от передачи каждой строки через `postMessage`. Диагностические правила продолжают работать в фоне, даже когда пользователь закрыл страницу расширения.

Второй слой — страницы, секции деталей и диалоги. Их интерфейсы запускаются в изолированных iframe без доступа к сети и обмениваются с приложением JSON-сообщениями. В наборе командных расширений таких интерфейсов 103.

Третий слой — бэкенд в виде WebAssembly-компонента под wasmtime, без доступа к файлам и окружению. Он нужен для сложных проверок конфигурации, инструментов AI-агентов и сервисных интеграций вроде API Argo CD. Такой бэкенд есть у четырёх пакетов: Flux, Argo CD, Argo Rollouts и Service mesh. Для остальных задач хватает манифеста и страниц.

## Как выглядит проверка в манифесте

Показательный случай — диагностика резервного копирования CloudNativePG. Правило относится к ресурсу `Cluster` из группы `postgresql.cnpg.io` и срабатывает при двух условиях:

- у объекта отсутствует `.metadata.deletionTimestamp`;
- condition `LastBackupSucceeded` имеет статус `False`.

Первая проверка исключает объекты, которые уже удаляются. Вторая связывает проблему с конкретным состоянием последнего бэкапа. Логика задаётся данными, поэтому хост может выполнять её без открытого интерфейса интеграции.

Для того же ресурса вычисляемая колонка читает `.status.phase`. Если аннотация `cnpg.io/hibernation` равна `on`, она показывает `Hibernated` с приглушённым оформлением. Такое исключение тоже помещается в манифест: отдельный обработчик страницы для него не нужен.

Декларативность влияет и на проверку доступа. Окно согласия показывает запрашиваемые виды ресурсов, точный текст PromQL и аргументы команд. Все три слоя обращаются к кластеру через общую проверку прав на Rust — ту же, которой пользуются AI-агенты. При оценке пакета администратор видит конкретный набор операций, доступных расширению.

## Совместимость проверяют старыми пакетами

За время развития платформы появились правила проблем, метрики, команды в подах, собственные виды в таблицах, сервисы, инструменты для агентов и связи между объектами. В манифесте требуемый уровень API задаётся полем `sextantApi`.

Контракт расширяют с сохранением прежнего смысла существующих возможностей. Для проверки в репозитории хранят замороженные пакеты прошлых версий со старым SDK внутри. При каждом изменении их запускают против настоящего протокола, системы прав и среды выполнения бэкенда. Это проверяет более широкий участок системы, чем сравнение TypeScript-типов.

Обратная ситуация тоже учтена: если последнее расширение требует более свежий API, каталог предлагает последний релиз, совместимый с установленной версией Sextant. При раздельном обновлении клиента и интеграций такой подбор версии становится частью штатного процесса установки.

## С чего начинать собственную интеграцию

SDK находится в каталоге `sdk/` основного репозитория. Он включает типы, сгенерированные из Rust, клиент для страницы, UI-кит, переводы для 14 языков, бэкенд на TypeScript через `defineBackend` или на Rust, тестовый хост, упаковку и подпись minisign. Проверки SDK охватывают 781 тест.

Валидация манифеста в SDK и Rust использует общий набор тестовых случаев. Ошибки структуры можно обнаружить во время сборки пакета. Тестовый хост позволяет проверять страницы без запуска Sextant.

Для первой версии интеграции полезно выписать ресурсы оператора, нужные колонки и условия проблем. Если задача укладывается в эти сущности, её можно описать манифестом. Страница понадобится для собственного интерфейса; WebAssembly-бэкенд — для логики, которой недостаточно декларативных средств.

В качестве образцов доступны 32 пакета в каталоге `extensions/`. Их README устроены одинаково: функции, запрашиваемые права с объяснениями, диагностические правила и команды. Для homelab с несколькими операторами это удобная точка проверки перед установкой: можно сопоставить возможности пакета с реально используемыми ресурсами и заранее изучить операции, которые он сможет выполнять.
